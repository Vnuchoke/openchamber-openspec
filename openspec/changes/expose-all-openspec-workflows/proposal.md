# Proposal

## Why

The extension exposes only part of OpenSpec's workflow vocabulary, and some existing actions do not
mean what their names suggest: card Propose completes an existing scaffold, while Archive all is
not the interactive Bulk archive workflow. Users need access to all twelve workflows without
confusing artifact creation with implementation or accidentally submitting a prompt.

## What Changes

- Add an SDK-native board `Workflows` menu for Propose change, Explore ideas, New change,
  Fast-forward, Bulk archive and Onboard. These prepare unsent current-chat prompts; they do not
  create changes, initialize OpenSpec or start sessions themselves.
- Add the same SDK-native `Workflows` menu to each available change's card and detail for Continue
  change, Apply tasks, Update change, Sync specs, Archive change, Verify change and contextual
  Explore ideas. Dispatch each named workflow explicitly, independently of the board stage; let
  the workflow check its current prerequisites.
- **BREAKING (interaction):** replace the Planning primary `propose` action with `Continue artifacts`,
  invoking Continue for one next artifact rather than completing the whole plan. Keep canonical
  Propose and Fast-forward as global workflows starting from the user's request.
- Rename the direct `new change` button to `Create scaffold…`; retain its name-and-goal dialog,
  validation, scoped CLI write and uncertain-outcome reconciliation. The separate New change
  workflow only prepares a prompt for the agent.
- Preserve Apply's explicit new-worktree option and the separately confirmed, completed-only
  `Archive all` session launch. Add canonical Bulk archive as an independent unsent workflow, not
  a replacement for that shortcut.
- Reuse the current composer-replacement and error-reporting behavior, context guards and retained
  UI handles. Add no polling, workflow-triggered board reads, automatic retries, SDK upgrades,
  service routes, dependencies or installation permissions.
- Document the full workflow skill set generated by OpenSpec 1.16.0 and the distinction between
  preparing a prompt and executing it. Skill installation or agent authorization remains the
  user's environment responsibility; do not silently substitute a different workflow.
- Apply sentence case to extension-owned buttons, preserving names, acronyms and change IDs.
  Add outcome-oriented button-hover descriptions without replacing accessible names;
  distinguish unsent drafts, direct scaffold writes and confirmed session/worktree launches.
- While any Workflows list is open, suppress its trigger description and every description outside
  that list. Describe each active workflow on pointer hover or keyboard navigation within its row,
  without covering the list or neighboring actions. Restore ordinary descriptions after dismissal.
- Ordinary button descriptions are visible only over their owner button and disappear immediately
  on pointer exit, including movement onto the description. Keyboard focus alone does not show or
  retain them. Inline Workflows descriptions keep pointer and keyboard activation unchanged.

## Capabilities

### New Capabilities

None. Workflow access belongs to the existing change-workflows capability.

### Modified Capabilities

- `change-workflows`: expose all twelve named workflows with explicit global/change targeting,
  canonical planning semantics, accessible menus and unchanged send-versus-compose boundaries.

## Impact

- UI ownership remains in `src/panel/controller.ts`, `workflow.ts`, `primary-action.ts`,
  `board-view.ts` and `detail-view.ts`. The additional user-requested UI pass also covers existing
  help/document/tasks views and create/delete/archive dialogs, with tooltip styles in `panel/index.html`.
  Keep prompt definitions and workflow identities shared between board and detail.
- Extend only `test/panel.test.mjs` at the user-approved fake-SDK-host seam. The user also approved
  an `OPENSPEC_TEST_BROWSER` selector in that existing fixture, defaulting to Chromium, for focused
  Firefox/WebKit panel runs. No new test file or helper is required.
- Update README setup/usage guidance and regenerate the installable panel bundle during
  implementation. Existing service behavior, private protocol, stage derivation and persisted
  change metadata do not change.
- Existing consumers see two label/behavior changes and additional workflow skill requirements.
  SDK 1.24.2 already provides the required menu and compose contracts. There are no new CLI
  commands, flags or output fields and no new capability-approval prompt.
- This change covers access and prompt routing, not successful agent execution under every skill
  profile or allowlist. The implementation must report actual browser coverage: the existing
  full check uses Chromium; focused panel runs add Firefox and WebKit rather than pretending all
  unrelated browser suites have become cross-engine.
